# Uber: system design — текст для презентации

Содержимое слайдов.
Основа истории — статья [A Brief History of Scaling Uber](https://highscalability.com/brief-history-of-scaling-uber/) (Josh Clemm, Senior Director of Engineering в Uber Eats, 2024).

План:

1. Что делает Uber и в каком масштабе (слайды 1–4).
2. Требования: функциональные и нефункциональные (слайды 5–6).
3. История развития и масштабирования 2009–2026 (слайды 7–22).
4. Выводы (слайды 23–24).

## Часть 1. Задача и масштаб

### Слайд 1. Uber: как масштабировать заказ поездки

- Название доклада.
- Фраза-идея: «Push a button and get a ride».

### Слайд 2. Что делает система

- Uber — двусторонний рынок в реальном времени.
- Спрос динамический: пассажир заказывает в любой момент из любой точки.
- Предложение динамическое: водитель постоянно двигается.
- Задача: свести спрос и предложение за секунды.

### Слайд 3. Масштаб сегодня

| Метрика | Значение |
|---|---|
| Страны и города | 70+ стран, 10 500+ городов |
| Активные пользователи в месяц (MAPC) | 208 млн (Q2 2026) |
| Поездки и доставки | 3,9 млрд за квартал (Q2 2026) ≈ 42 млн в день |
| Водители и курьеры | ~10 млн (конец 2025) |
| Бэкенд | 4 000+ stateless-микросервисов, 250 000+ серверов |
| Хранилища | десятки ПБ данных, десятки млн запросов в секунду |
| Fulfillment (исполнение заказов) | 1 млн одновременных пользователей, миллиарды транзакций в день |

### Слайд 4. Как рос масштаб

| Год | Масштаб |
|---|---|
| 2009 | Друзья основателей в Сан-Франциско |
| 2011–2015 | Рост в 38 раз за 4 года |
| 2014 | Поездки растут на ~20 % в месяц |
| Дек. 2015 | 1 млрд поездок |
| 2016 | 2 млрд поездок |
| Май 2017 | 5 млрд поездок |
| Июнь 2018 | 10 млрд поездок, 600 городов |
| Q2 2026 | 3,9 млрд поездок за один квартал |

## Часть 2. Требования

### Слайд 5. Функциональные требования

Основные (входят в дизайн):

1. Пассажир указывает точку посадки и точку назначения. Система показывает цену и ETA (расчётное время прибытия).
2. Пассажир заказывает поездку по этой цене.
3. Система находит ближайшего свободного водителя. Этот шаг дальше называется «матчинг».
4. Водитель принимает или отклоняет заказ.
5. Водитель едет к пассажиру и к точке назначения по навигации.
6. Пассажир видит машину на карте в реальном времени.

Вне рамок (есть в продукте, но не в этом дизайне):

- оплата и выплаты водителям;
- рейтинги и отзывы;
- surge pricing (динамическое ценообразование);
- совместные поездки (Pool), поездки по расписанию;
- Uber Eats и доставка посылок.

### Слайд 6. Нефункциональные требования

| Требование | Цель | Почему |
|---|---|---|
| Время матчинга | < 1 мин | Пассажир уходит к конкуренту, если ждёт долго |
| Консистентность матчинга | строгая | Один водитель — один заказ, одна машина — один пассажир |
| Пиковая нагрузка | 100 тыс. заказов из одной зоны | Концерт, матч, Новый год |
| Доступность | 99,99 % | Переход к конкуренту стоит пассажиру один клик |
| Свежесть локаций | 4–5 с | Устаревшая позиция — неверный ETA и плохой матчинг |
| Сохранность поездки | без потерь при отказе ДЦ | Поездка — это деньги и безопасность людей |
| Идемпотентность | любой запрос можно повторить | Повтор не должен создать два заказа или два списания |

## Часть 3. История развития и масштабирования

### Слайд 7. Карта эпох

| Год | Этап | Главная проблема |
|---|---|---|
| 2009 | LAMP-прототип | Не масштабируется, гонки при матчинге |
| 2011 | Два монолита | API-монолит растёт, деплой рискованный |
| 2013–2015 | Микросервисы | Операционная сложность |
| 2014 | Schemaless | Один PostgreSQL на всю компанию |
| 2014–2015 | Новый dispatch, RTAPI, Ringpop | Dispatch умеет только «1 водитель — 1 пассажир» |
| 2016 | Мобильная архитектура RIBs | Мобильный монолит |
| 2017 | Uber Eats | Трёхсторонний рынок |
| 2018 | Project Ark, H3 | Тысячи сервисов, 12 000 репозиториев |
| 2020 | DOMA, Edge Gateway | Распределённый монолит |
| 2021 | Fulfillment на Spanner | Ставка на доступность, расхождения данных |
| 2023+ | Облако | 250 000+ своих серверов |

### Слайд 8. 2009: LAMP-прототип

- Первую версию написали подрядчики.
- Стек LAMP: Linux, Apache, MySQL, PHP.
- Код написан на испанском.
- Запуск: друзья основателей в Сан-Франциско, один продукт — UberBLACK.
- Проблема: гонки при матчинге. Одному пассажиру отправляли две машины. Одного водителя назначали на два заказа.

### Слайд 9. 2011: два монолита

- **Dispatch** на Node.js + MongoDB (позже Redis): матчинг и локации в реальном времени.
- **API** на Python + PostgreSQL: аутентификация, промокоды, расчёт цены.
- **ON (Object Node)** — слой между dispatch и API. Dispatch продолжает работать, если API падает.
- Uber — один из первых крупных пользователей Node.js в продакшене.

### Слайд 10. 2013–2015: переход на микросервисы

- API-монолит разделили на сервисы: биллинг пассажиров, выплаты водителям, антифрод, аналитика, управление городами.
- ~100 сервисов к 2014 году, 500+ к 2015–2016 году.
- Основной стек: Python + Tornado.

| Проблема микросервисов | Решение Uber |
|---|---|
| Сервисы написаны по-разному | Clay — единый фреймворк поверх Flask |
| Поиск сервисов, отказоустойчивость | TChannel + Hyperbahn: свой RPC, service discovery, rate limiting, circuit breaking |
| Слабые контракты между сервисами | Apache Thrift (позже gRPC + Protobuf) |
| Риск выкатки | Flipr — feature flags |
| Наблюдаемость | M3 — метрики, Nagios — алерты |
| Трассировка запросов | Merckx, затем Jaeger |

### Слайд 11. 2014: кризис базы поездок

- Вся компания работает на одном PostgreSQL.
- Больше всего места занимают поездки, и они растут быстрее всего: ~20 % в месяц.
- Прогноз: к концу 2014 года место и IOPS закончатся.
- Дедлайн: Хэллоуин, 31 октября — одна из самых нагруженных ночей года.
- Проблемы Postgres: не хватает CPU и памяти, сложно добавить таблицу или индекс.

### Слайд 12. 2014: почему MySQL, а не Postgres

| Проблема Postgres | Суть |
|---|---|
| Write amplification | Изменение одного поля обновляет все индексы таблицы |
| Репликация | WAL пишет физические изменения диска: много трафика между ДЦ |
| Повреждение данных | Баг 9.2: реплики расходились, дублировались строки |
| MVCC на репликах | Долгие чтения на реплике отменяются или реплика отстаёт |
| Обновление версий | Физическая репликация не работает между major-версиями: часы простоя |
| Соединения | Процесс на соединение: дорого при сотнях соединений |

Причины Uber подробно описал в статье 2016 года «Why Uber Engineering Switched from Postgres to MySQL».

### Слайд 13. 2014: Schemaless и Project Mezzanine

- **Schemaless** — своё хранилище поездок поверх MySQL.
  - Модель: append-only, разреженная трёхмерная hash map, как Google Bigtable.
  - Ячейка неизменяемая. Адрес ячейки: row key (UUID) + имя колонки + ref key (версия).
  - 4 096 шардов. Горизонтальное масштабирование добавлением серверов.
  - Триггеры: изменение данных запускает обработку, например биллинг.
- **Project Mezzanine** — миграция:
  - ~5 месяцев от идеи до продакшена, финальные 6 недель — war room;
  - ID поездок заменили на UUID, сотни SQL-запросов переписали;
  - двойная запись в обе БД, сравнение результатов в фоне;
  - переключение в конце сентября 2014 года, без алертов и инцидентов.
- Cassandra заменила Postgres для других данных, включая БД матчинга.

### Слайд 14. 2014–2015: разделение dispatch

- Dispatch делал две работы: матчинг и проксирование всего трафика к сервисам.
- Решение: разделить на две части.
  - **RTAPI (Real-Time API)** — шлюз для мобильных приложений на Node.js. Первая версия Uber Eats целиком жила в нём.
  - **Новый dispatch** — набор сервисов:
    - Supply Service — водители, их машины и состояние;
    - Demand Service — заказы и требования пассажиров, а также еда и посылки;
    - DISCO (dispatch optimization) — матчинг спроса и предложения.

### Слайд 15. 2014–2015: гео-индекс и Ringpop

- **Гео-индекс на Google S2:**
  - Земля делится на ячейки, у каждой ячейки свой ID;
  - уровень 12: ячейка 3–6 км²;
  - ID ячейки — ключ шардирования;
  - запрос: покрыть круг вокруг пассажира ячейками и опросить их шарды;
  - цель: 1 млн записей в секунду, координаты каждые 4 с.
- **Ringpop** — библиотека для stateful-сервисов на Node.js:
  - consistent hashing (консистентное хеширование) распределяет ключи по узлам;
  - gossip-протокол на базе SWIM узнаёт, какие узлы живы;
  - любой узел принимает запрос и пересылает его владельцу ключа;
  - масштаб: тысячи узлов; выбирает доступность, а не консистентность.
- **TChannel** — свой RPC-протокол, по оценке Uber в 20 раз быстрее HTTP.

### Слайд 16. 2015: принципы надёжности

- Любой запрос можно повторить: все запросы идемпотентны.
- Любой процесс можно убить: случайное падение не ломает систему.
- Crash-only: нет graceful shutdown, тестируют только внезапные падения.
- Мелкие части: нет единой точки отказа и нет пар. Потеря одного из двух — это минус 50 % мощности.
- Убивать можно всё, включая базы данных.
- Backup requests: запрос уходит во вторую реплику с задержкой. Первый ответ отменяет второй запрос.
- Отказ дата-центра: телефон водителя хранит зашифрованный state digest (сводку состояния поездки). Резервный ДЦ запрашивает сводку и продолжает поездку.

### Слайд 17. 2016: мобильная архитектура

- Проблема: сотни инженеров, одна кодовая база, один релиз на всех.
- **RIBs** (Router, Interactor, Builder): каждая часть экрана — отдельный модуль своей команды.
- Основной код проходит строгое ревью, дополнительный включают через feature flags.

### Слайд 18. 2015–2017: Uber Eats

- Конец 2015 года: запуск в Торонто.
- Рост такой же быстрый, как у UberX.
- Переиспользовали dispatch, fulfillment, оплату.
- Новое: корзина, меню, поиск, каталог.
- Рынок стал трёхсторонним: клиент, ресторан, курьер.
- Сегодня: 0–N клиентов (групповой заказ), N ресторанов (заказ из нескольких), 0–N курьеров (крупный заказ, своя доставка ресторана).

### Слайд 19. 2018: Project Ark и H3

- Культура «Let Builders Build» дала скорость, но и хаос:
  - тысячи микросервисов, 12 000 репозиториев;
  - несколько очередей, БД, протоколов, языков для одних и тех же задач;
  - «пять-шесть систем бонусов, похожих друг на друга на 75 %» — Туан Фам, CTO Uber.
- **Project Ark:**
  - Java и Go — основные языки бэкенда, Python и JavaScript — устаревшие;
  - репозитории свели к основным языкам: Java, Go, iOS, Android, web;
  - стандартные слои: клиент, представление, продукт, бизнес-логика;
  - общие библиотеки для трассировки, логирования, сети и отказоустойчивости.
- **H3** — открытый гексагональный гео-индекс (open source в 2018 году):
  - у шестиугольника все 6 соседей на одном расстоянии от центра;
  - 16 уровней детализации, ячейка следующего уровня в ~7 раз меньше;
  - применение: surge pricing, dispatch, аналитика рынка.

### Слайд 20. 2020: DOMA и Edge Gateway

- Проблема: ~2 200 критичных микросервисов.
  - Для отладки инженер проходил ~50 сервисов 12 команд.
  - Простая фича требовала работы многих команд.
  - Сервисы приходилось деплоить вместе — распределённый монолит.
- **DOMA** (Domain-Oriented Microservice Architecture):
  - домены — группы сервисов по смыслу: карты, цены, матчинг;
  - слои — сервис может зависеть только от нижних слоёв;
  - шлюз — одна точка входа в домен;
  - точки расширения — команды добавляют логику без правки ядра.
- **Edge Gateway** заменил RTAPI на Node.js. Слои: Edge → Presentation → Product → Domain.
- Результат: 2 200 сервисов → 70 доменов, интеграция фичи 3 дня → 3 часа, онбординг быстрее на 25–50 %.

### Слайд 21. 2020–2021: Docstore и fulfillment на Spanner

- **Docstore** вырос из Schemaless:
  - транзакционная БД поверх MySQL;
  - строгая сериализуемость внутри партиции, Raft, консистентность важнее доступности;
  - вместе со Schemaless: десятки ПБ, десятки млн запросов в секунду.
- **Fulfillment Platform** переписали с нуля:
  - проблема: Ringpop + Cassandra выбирали доступность, при split-brain данные расходились;
  - запись нескольких сущностей шла через цепочку RPC с промежуточными несогласованными состояниями;
  - 400+ инженеров меняли ядро без общих правил.
- Требования к новой платформе: транзакции между регионами, 99,99 % SLA, нет потери данных, смена схемы без простоя.
- Выбор: Google Cloud Spanner — ACID-транзакции между шардами, автоматическое шардирование.
- Результат: 120+ сценариев исполнения заказа, 1 млн одновременных пользователей.

### Слайд 22. 2023+: облако

- 250 000+ серверов в своих дата-центрах.
- Проблемы: инструменты не успевают за ростом парка, новые регионы требуют новых ДЦ, размер парка нужно постоянно подбирать.
- 4 000+ stateless-микросервисов сделали переносимыми.
- **Project Crane** — единый стек для облака и своих ДЦ.
- Миграция в Google Cloud и Oracle Cloud в ближайшие годы.
- Поиск: Elasticsearch → свой движок Sia (2019) → OpenSearch (2024).

## Часть 4. Выводы

### Слайд 23. Цикл, который повторяет Uber

| Этап | Что делает Uber | Примеры |
|---|---|---|
| Старт | Берёт готовые инструменты | PostgreSQL, Elasticsearch, Node.js |
| Быстрый рост | Строит свои системы | Schemaless, Ringpop, TChannel, Sia |
| Стабилизация | Упрощает и возвращается к стандартам | Spanner, Docstore, gRPC, OpenSearch, DOMA |

### Слайд 24. Уроки

1. Разные данные — разные требования к консистентности: локациям хватает итоговой согласованности, матчингу и деньгам нужна строгая.
2. Главная нагрузка — поток координат, а не заказы.
3. Микросервисы без инструментов и границ превращаются в распределённый монолит.
4. Миграцию данных проводят через двойную запись и сверку, а не через «большой рубильник».
5. Своя система оправдана, пока стандартная не справляется. Потом её стоит заменить.
