## 1. Текст: анализ тональности отзывов

Скрипт: `task1-ml-models/text_sentiment.py`
Запуск: `uv run python task1-ml-models/text_sentiment.py`

### Постановка задачи (ТЗ)

Автоматически определять тональность англоязычного отзыва о фильме: позитивный или негативный.

- **Вход:** строка (текст отзыва произвольной длины).
- **Выход:** `{"label": "POSITIVE" | "NEGATIVE", "score": float}`, где `score` это уверенность модели в диапазоне 0..1.
- **Сценарий использования:** разметка потока отзывов без участия модератора, сортировка обращений, агрегированная аналитика («доля негатива по фильму»).
- **Требования:** работа локально, скорость ≥ 10 текстов/с, accuracy ≥ 0.85 на отзывах из другого источника, чем обучающие данные.
- Модель планируется обернуть в API, поэтому интерфейс сделан как чистая функция `predict(text) -> dict`.

### 1) Преимущества выбранной библиотеки (Hugging Face Transformers)

- **Единый API `pipeline`:** токенизация, модель и постобработка вызываются одной строкой. Одинаковый код подходит для тысяч моделей с Hub.
- **Hugging Face Hub:** готовые предобученные модели с карточками, где описаны датасет обучения, метрики и ограничения.
- **Библиотека `datasets`** из той же экосистемы: загрузка IMDB для проверки занимает одну строку.
- **Поддержка ускорителей:** параметр `device="mps"` запускает модель на GPU Apple Silicon без изменения кода.
- **Прозрачность:** при необходимости pipeline раскладывается на `AutoTokenizer` + `AutoModelForSequenceClassification`, то есть это не «чёрный ящик».

### 2) Принцип работы модели и причины выбора

**Модель:** `distilbert/distilbert-base-uncased-finetuned-sst-2-english` (~67M параметров, ~260 МБ).

Как работает:
1. **Токенизация (WordPiece).** Текст приводится к нижнему регистру (`uncased`) и режется на subword-токены. Редкие слова раскладываются на части (`unbelievable` → `un`, `##bel`, `##ie`, `##vable`), поэтому словарь в ~30k токенов покрывает любые тексты. В начало добавляется служебный токен `[CLS]`.
2. **Трансформер-энкодер (6 слоёв).** Механизм self-attention позволяет каждому токену учитывать все остальные токены текста. Поэтому представление слова зависит от контекста: `good` в «not good» и в «very good» получает разные векторы.
3. **Агрегация.** Итоговый 768-мерный вектор токена `[CLS]` используется как представление всего текста.
4. **Классификатор.** Линейный слой 768 → 2 и softmax дают вероятности классов NEGATIVE/POSITIVE.

**DistilBERT** это сжатая версия BERT, полученная **дистилляцией знаний**: маленькую модель (student) обучали воспроизводить выходы большой (teacher). В результате модель на 40% меньше и на 60% быстрее BERT при сохранении ~97% его качества. Затем её дообучили (fine-tune) на **SST-2** под задачу тональности.

**Причины выбора:**
- одна из самых используемых моделей тональности на Hugging Face, проверенная сообществом;
- маленькая и быстрая: подходит для API и работает даже на CPU;
- домен обучения (рецензии на фильмы) совпадает с нашим сценарием.

### 3) Структура данных

**Данные обучения модели (SST-2, Stanford Sentiment Treebank):** ~67k коротких фраз из рецензий на фильмы с бинарной меткой (0 = negative, 1 = positive). Модель мы не обучали, она уже дообучена авторами.

**Данные для проверки (инференса): IMDB (`stanfordnlp/imdb`, split `test`):**

| Поле | Тип | Описание |
|---|---|---|
| `text` | str | полный текст рецензии, часто несколько абзацев, встречается HTML-разметка `<br />` |
| `label` | int | 0 = negative, 1 = positive |

- Весь test-сплит содержит 25 000 отзывов, классы сбалансированы.
- Для оценки взята случайная выборка из **500 отзывов** (`seed=42`): 254 негативных, 246 позитивных.
- **Почему IMDB, а не SST-2:** на SST-2 модель обучалась, поэтому проверка на нём не показала бы, как модель обобщает. IMDB это тот же домен (кино), но другой источник и гораздо более длинные тексты, то есть честная проверка вне обучающего распределения.

**Формат инференса:** строка → токены (≤ 512, длиннее обрезаются, `truncation=True`) → логиты `[1, 2]` → `{"label", "score"}`.

### 4) Метрики качества

#### ML-метрики (500 отзывов IMDB, MPS)

| Класс | Precision | Recall | F1 | Support |
|---|---|---|---|---|
| neg | 0.873 | 0.917 | 0.894 | 254 |
| pos | 0.910 | 0.862 | 0.885 | 246 |
| **Accuracy** | | | **0.890** | 500 |
| Macro avg | 0.891 | 0.890 | 0.890 | 500 |

- **Accuracy** это доля правильных ответов. Классы сбалансированы, поэтому метрика показательна.
- **Precision** (точность) показывает, какая доля отзывов, названных моделью позитивными, действительно позитивна.
- **Recall** (полнота) показывает, какую долю всех позитивных отзывов модель нашла.
- **F1** это гармоническое среднее precision и recall.
- **Вывод:** recall класса `neg` (0.917) выше, чем у `pos` (0.862). Модель немного смещена в сторону «негатива»: часть позитивных отзывов она ошибочно считает негативными.

#### Инфраструктурные метрики

| Устройство | Скорость | Латентность |
|---|---|---|
| MPS (GPU Apple M5), batch 16 | **63.1 текста/с** | 15.9 мс/текст |
| CPU, batch 16 (100 отзывов) | 26.6 текста/с | 37.6 мс/текст |

- Ускорение на GPU в ~2.4 раза. Первый прогон (warm-up) из замера исключён.
- Качество на CPU (accuracy 0.900 на 100 отзывах) совпадает с MPS в пределах разброса выборки: модель та же, отличается только устройство.

#### Продуктовые метрики (для внедрения)

- доля отзывов, размеченных автоматически без проверки человеком (например, при `score > 0.95`);
- время модерации одного отзыва и нагрузка на модераторов;
- доля жалоб на неверную разметку.

### 5) Особенности реализации, эффективность и ограничения

**Реализация:**
- Модель загружается один раз при импорте модуля, `predict()` только выполняет инференс. Это важно для будущего API: модель не перезагружается на каждый запрос.
- Пакетная обработка (`batch_size=16`) даёт выигрыш по скорости на GPU по сравнению с поштучной.
- `truncation=True` обязателен: DistilBERT принимает не более 512 токенов, а многие отзывы IMDB длиннее.

**Ограничения (по результатам анализа 55 ошибок из 500):**
1. **Сарказм и ирония.** «Oh great, another sequel nobody asked for» модель считает позитивным (score 0.85): слово *great* перевешивает.
2. **Длинные тексты.** Модель видит только первые 512 токенов, а итоговое мнение автора часто стоит в конце рецензии.
3. **Пересказ сюжета.** Когда большая часть отзыва описывает мрачный сюжет, а не мнение автора, модель путает тон сюжета с оценкой фильма.
4. **Только английский язык** и бинарная шкала: нет нейтрального класса.

**Возможные улучшения (без обучения):**
- для длинных текстов разбивать отзыв на куски по 512 токенов и усреднять предсказания;
- взять модель крупнее (RoBERTa-large, обученная на отзывах), если важнее качество, а не скорость;
- для русского языка или трёх классов взять мультиязычную модель (например, `cardiffnlp/twitter-xlm-roberta-base-sentiment`).

## 2. Изображения: классификация (PyTorch / torchvision)

Скрипт: `task1-ml-models/image_classify.py`
Запуск: `uv run python task1-ml-models/image_classify.py` (нужен датасет, см. раздел 3)

### Постановка задачи (ТЗ)

Определять, что изображено на фотографии.

- **Вход:** изображение (JPEG/PNG, любой размер, RGB).
- **Выход:** топ-5 классов из 1000 классов ImageNet с вероятностями, например `[("tench", 0.57), ("barracouta", 0.002), ...]`.
- **Сценарий использования:** автоматическая категоризация фото (каталог товаров, фотобанк, модерация), поиск по содержимому.
- **Требования:** локальный запуск, ≥ 50 изображений/с на GPU, top-5 accuracy ≥ 0.9 на изображениях известных модели классов.

### 1) Преимущества выбранной библиотеки (PyTorch + torchvision)

- **Веса и препроцессинг в одном объекте:** `ResNet50_Weights.DEFAULT` содержит и веса, и `transforms()` (resize, crop, нормализацию), и список названий классов. Так исключается частая ошибка «подали картинку не в том формате, на котором модель обучалась».
- **Эталонные реализации архитектур** (ResNet, EfficientNet, ViT, ConvNeXt и др.) с опубликованными метриками на ImageNet.
- **Нативный PyTorch:** модель это обычный `nn.Module`. Её легко встроить в свой код, взять как экстрактор признаков или дообучить.
- **Готовые утилиты данных:** `ImageFolder` читает датасет вида «папка = класс» одной строкой, `DataLoader` собирает батчи.
- **Поддержка MPS** (GPU Apple Silicon) через `.to("mps")`.

Это второй фреймворк в работе (первый: Hugging Face Transformers).

### 2) Принцип работы модели и причины выбора

**Модель:** ResNet-50, веса `IMAGENET1K_V2` (~25.6M параметров, ~98 МБ).

Как работает:
1. **Свёрточные слои.** Небольшие фильтры (3×3, 1×1) скользят по изображению и выделяют локальные признаки. Ранние слои реагируют на края и цветовые пятна, средние на текстуры и формы, глубокие на части объектов (морда собаки, колесо, окно).
2. **Residual-связи** (ключевая идея ResNet). Выход блока равен `F(x) + x`: блок учится предсказывать только «поправку» к входу, а сигнал и градиент проходят через «короткое замыкание» без изменений. Это решило проблему затухания градиента и позволило обучать сети глубиной 50–150 слоёв.
3. **Bottleneck-блоки:** в ResNet-50 каждый блок сжимает каналы свёрткой 1×1, применяет свёртку 3×3 и расширяет обратно. Так глубокая сеть остаётся относительно дешёвой по вычислениям.
4. **Классификатор.** Global average pooling сворачивает карту признаков в вектор из 2048 чисел, затем линейный слой 2048 → 1000 и softmax выдают вероятности классов.

**Препроцессинг (`weights.transforms()`):** resize до 232 px по короткой стороне → центральный кроп 224×224 → перевод в тензор [0,1] → нормализация по mean/std ImageNet. На выходе тензор `[1, 3, 224, 224]`.

**Причины выбора:**
- классический и хорошо изученный бейзлайн компьютерного зрения;
- веса V2 обучены по улучшенному рецепту torchvision: **top-1 80.9% / top-5 95.4% на ImageNet** (по документации torchvision), против 76.1% у исходных весов V1;
- умеренный размер: быстрый инференс на MPS и приемлемый на CPU.

### 5) Особенности реализации, эффективность и ограничения

**Реализация:**
- `model.eval()` переключает BatchNorm в режим инференса (используются накопленные статистики, а не статистики батча). Без этого предсказания зависят от состава батча.
- `torch.inference_mode()` отключает построение графа градиентов: меньше памяти и выше скорость.
- `unsqueeze(0)` добавляет размерность батча: `[3,224,224]` → `[1,3,224,224]`.
- Модель кэшируется по устройству и загружается один раз.
- Перед замером делается прогревочный прогон (warm-up), чтобы инициализация GPU не попала в метрику.

**Ограничения:**
1. **Фиксированный набор из 1000 классов.** Объекты вне ImageNet модель всё равно отнесёт к одному из 1000 классов (с малой уверенностью).
2. **Путаница близких классов** (см. анализ ошибок). ImageNet содержит очень детальные классы (120 пород собак), а в прикладной задаче часто достаточно грубой категории.
3. **Низкая абсолютная уверенность.** Даже на верных ответах вероятность часто 0.2–0.6 (например, tench 0.57). Веса V2 обучены с label smoothing, поэтому softmax «размазан». Порог уверенности надо подбирать на данных, а не брать 0.9 «по привычке».
4. **Разрешение.** Изображения Imagenette-160 увеличиваются до 232 px при препроцессинге, и мелкие детали теряются. На полноразмерных фото качество должно быть выше.

**Возможные улучшения (без обучения):**
- ограничивать выбор категориями задачи (как в метрике «среди 10 классов») или объединять близкие классы ImageNet в одну категорию;
- взять более современную модель (EfficientNetV2, ConvNeXt, ViT) из того же torchvision: точнее, но медленнее;
- для открытого набора категорий использовать zero-shot модель CLIP: классы задаются текстом, и 1000 классов ImageNet больше не ограничение.

## 3. Аудио: распознавание речи (Hugging Face Transformers, Whisper)

Скрипт: `task1-ml-models/audio_stt.py`
Запуск: `uv run python task1-ml-models/audio_stt.py`. Скрипт транскрибирует все `.wav/.mp3/.m4a` из `task1-ml-models/data/`.

### Постановка задачи (ТЗ)

Переводить речь из аудиофайла в текст (speech-to-text, ASR).

- **Вход:** аудиофайл (wav/mp3/m4a) или массив сэмплов + частота дискретизации.
- **Выход:** строка с распознанным текстом (с пунктуацией и регистром).
- **Сценарий использования:** расшифровка голосовых сообщений и созвонов, субтитры к видео, голосовой ввод.
- **Требования:** локальная работа без облачных API, поддержка русского и английского, скорость выше реального времени (RTF < 1), WER ≤ 10% на чистой английской речи.

### 1) Преимущества выбранной библиотеки (Hugging Face Transformers)

- **Тот же `pipeline`, что и для текста:** `pipeline("automatic-speech-recognition")` сам делает ресемплинг, извлечение признаков, генерацию и декодирование токенов в текст.
- **Длинные файлы «из коробки»:** с `return_timestamps=True` пайплайн режет аудио на окна по 30 с и склеивает результат.
- **Смена модели одной строкой:** `whisper-tiny` / `small` / `medium` / `large-v3` взаимозаменяемы. Благодаря этому сравнение размеров моделей занимает минуты.
- **Встроенный нормализатор текста Whisper** (`tokenizer.normalize`) для корректного подсчёта WER.
- **Поддержка MPS** на Apple Silicon.

### 2) Принцип работы модели и причины выбора

**Модель:** OpenAI Whisper, основной вариант `whisper-small` (244M параметров), для сравнения `whisper-tiny` (39M).

Как работает:
1. **Препроцессинг.** Аудио приводится к 16 кГц моно и режется на окна по 30 секунд.
2. **Лог-мел-спектрограмма.** Сигнал превращается в «картинку» размером 80 мел-полос × 3000 кадров. По горизонтали время, по вертикали частоты в мел-шкале (она повторяет восприятие частот человеком), яркость показывает энергию.
3. **Энкодер (трансформер)** превращает спектрограмму в последовательность векторов-признаков звука.
4. **Декодер (трансформер)** авторегрессионно генерирует текстовые токены один за другим. Через cross-attention он «смотрит» на выход энкодера. В начале последовательности стоят служебные токены: язык (`<|ru|>`, `<|en|>`), задача (`transcribe` или `translate`), наличие таймкодов. Поэтому одна модель умеет и распознавать 99 языков, и переводить на английский.
5. **Обучение:** 680 тыс. часов размеченного аудио из интернета (weak supervision). Отсюда устойчивость к шуму, акцентам и разным микрофонам без дообучения.

**Причины выбора:**
- одна из лучших открытых моделей ASR, работает с русским без дополнительных моделей;
- пунктуация и регистр в выходе, без отдельной модели постобработки;
- линейка размеров позволяет выбрать компромисс «качество / скорость». `small` это разумная середина: заметно точнее `tiny` и при этом в несколько раз быстрее реального времени на M5.

### 3) Структура данных

**Данные обучения модели:** 680k часов пар «аудио — транскрипт» с веба, из них ~117k часов на 96 языках, отличных от английского. Модель мы не обучали.

**Данные для проверки:**

1. **`hf-internal-testing/librispeech_asr_dummy`**, конфиг `clean`, split `validation`. Это 73 фрагмента английской начитанной речи (аудиокниги LibriSpeech), всего **481 секунда** аудио.

| Поле | Тип | Описание |
|---|---|---|
| `audio` | dict (`bytes`/`array`, `sampling_rate` = 16000) | звуковая волна |
| `text` | str | эталонная расшифровка ЗАГЛАВНЫМИ буквами без пунктуации |
| `speaker_id`, `chapter_id`, `id` | int/str | метаданные |

2. **Русская фраза** `data/ru_tts.wav` (~10 с, 16 кГц моно), синтезированная голосом Milena встроенного в macOS синтезатора (`say`), с известным эталонным текстом. Это позволяет посчитать WER и для русского языка.

**Формат инференса:** массив float32 16 кГц → лог-мел `[1, 80, 3000]` → токены → строка.

### 4) Метрики качества

#### ML-метрики

**WER (Word Error Rate)** = (S + D + I) / N, где S это замены слов, D пропуски, I вставки, N число слов в эталоне. 0 означает идеальное распознавание, 0.07 значит ошибку в 7 словах из 100.

Перед подсчётом WER тексты **нормализуются**: Whisper пишет с пунктуацией и заглавными буквами, а эталон LibriSpeech без них. Считаем две версии:
- **WER (простая нормализация):** нижний регистр, удаление пунктуации;
- **WER (нормализатор Whisper):** дополнительно приводит к одному виду сокращения, числа и британское/американское написание (`Mr` → `mister`, `colour` → `color`, `twenty dollars` → `$20`). Это стандарт при сравнении ASR-моделей.

| Модель | Параметров | WER (простая норм.) | S / D / I | **WER (норм. Whisper)** |
|---|---|---|---|---|
| whisper-tiny | 39M | 0.114 | 97 / 10 / 24 | **0.103** |
| whisper-small | 244M | 0.072 | 70 / 7 / 6 | **0.060** |

- Нормализация сама по себе «улучшает» WER на 1–1.2 п.п. Часть ошибок была не ошибками распознавания, а разницей в написании (`mister` против `Mr`). **Вывод:** WER нельзя сравнивать между работами без одинаковой нормализации.
- `small` почти вдвое точнее `tiny` (0.060 против 0.103). В частности, у `tiny` в 4 раза больше вставок лишних слов.

**Типичные оставшиеся ошибки** (одинаковы для обеих моделей):
- **имена собственные:** Leighton → Layton, Birket → Birkut, Carker → Karker. Модель пишет похоже звучащее, но более частое написание;
- **редкие слова:** similes → symbolies / similarly;
- **созвучные служебные слова:** in → an / and.

**Русский язык** (`ru_tts.wav`, whisper-small): **WER = 0.000**. Распознано дословно, с правильной пунктуацией:
> «Добрый вечер, сегодня мы проверяем, насколько хорошо модель распознает русскую речь. Рекомендательные системы помогают пользователям находить интересные фильмы и музыку.»

Ограничение этой проверки: синтезированная речь идеально чистая (без шума, акцента и оговорок), поэтому результат оптимистичнее, чем на живой записи.

#### Инфраструктурные метрики

**RTF (Real-Time Factor)** = время обработки / длительность аудио. RTF < 1 означает, что модель работает быстрее реального времени.

| Модель | Время на 481 с аудио (MPS) | RTF | Быстрее реального времени |
|---|---|---|---|
| whisper-tiny | 21.5 с | 0.045 | ~22× |
| whisper-small | 78.3 с | 0.163 | ~6× |

Русская фраза ~10 с распознаётся whisper-small за ~2.2 с.

**Компромисс качество/скорость:** `small` в 6 раз больше по параметрам и в ~3.6 раза медленнее `tiny`, но ошибается на 40% реже. Для офлайн-расшифровки выгоднее `small`. Для работы в реальном времени на слабом железе подойдёт `tiny`.

#### Продуктовые метрики (для внедрения)

- доля расшифровок, которые пользователь не редактирует;
- время от загрузки файла до готового текста;
- доля голосовых, для которых расшифровку открыли и прочитали (полезность функции).

### 5) Особенности реализации, эффективность и ограничения

**Реализация:**
- Пайплайн кэшируется по паре (модель, устройство) и загружается один раз.
- Язык задаётся явно (`generate_kwargs={"language": ...}`). Без этого Whisper определяет язык по первым секундам и может ошибиться на коротких фрагментах.
- `return_timestamps=True` включает обработку файлов длиннее 30 секунд.
- Пайплайн изменяет переданный словарь с аудио, поэтому на вход подаётся копия (`dict(audio)`).
- Перед замером скорости делается прогревочный прогон.

**Техническая проблема и её решение.** Библиотека `datasets` 5.x декодирует аудио через `torchcodec`, а `torchcodec` не поддерживает установленный FFmpeg 9. Вместо понижения версии FFmpeg аудио загружается без декодирования (`Audio(decode=False)`), и байты читаются через `soundfile`. Работает без лишних системных зависимостей.

**Ограничения:**
1. **Имена собственные и редкие термины** распознаются по созвучию.
2. **Галлюцинации на тишине и шуме.** Декодер является языковой моделью и на участках без речи может «досочинить» текст.
3. **Окно 30 секунд:** на стыках окон при склейке возможны пропуски или повторы слов.
4. **Скорость.** Крупные модели (`large-v3`) точнее, но на CPU работают медленнее реального времени.

**Возможные улучшения (без обучения):**
- `whisper-large-v3-turbo`: качество близко к large при скорости ближе к small;
- VAD (детектор речи) перед распознаванием, чтобы не подавать тишину и избежать галлюцинаций;
- `initial_prompt` со словарём терминов и имён для конкретной предметной области;
- оптимизированные рантаймы (`faster-whisper`, `whisper.cpp`, `mlx-whisper` для Apple Silicon) для ускорения в несколько раз.

## 4. Видео: детекция и трекинг объектов (Ultralytics YOLO)

Скрипт: `task1-ml-models/video_detect.py`
Запуск: `uv run python task1-ml-models/video_detect.py`. Скрипт обрабатывает все `.avi/.mp4/.mov` из `task1-ml-models/data/` и сохраняет размеченную копию `<имя>_out.mp4`.

### Постановка задачи (ТЗ)

Находить и отслеживать объекты (людей, автомобили и т.д.) на видео.

- **Вход:** видеофайл.
- **Выход:** видео с рамками, классами, уверенностью и ID трека для каждого объекта. Плюс статистика: число детекций по классам, число **уникальных** объектов, скорость обработки.
- **Сценарий использования:** подсчёт посетителей и трафика, видеоаналитика парковок и проходных, охрана периметра.
- **Требования:** обработка быстрее реального времени (FPS обработки ≥ FPS видео), локально, без облака.

### 1) Преимущества выбранной библиотеки (Ultralytics)

- **Детекция, сегментация, поза и трекинг** в одном API: `model.predict(...)`, `model.track(...)`, `model.val(...)`.
- **Готовые трекеры** (ByteTrack, BoT-SORT) подключаются одним параметром.
- **Встроенная валидация:** `model.val(data=...)` считает Precision, Recall, mAP50, mAP50-95 по стандарту COCO.
- **Удобный результат:** `r.boxes.xyxy`, `r.boxes.cls`, `r.boxes.conf`, `r.boxes.id`, а `r.plot()` сразу рисует разметку на кадре.
- **Экспорт** в ONNX, CoreML, TensorRT для продакшена.
- Работает поверх PyTorch, поддерживает MPS.

Это третий фреймворк в работе (после Hugging Face Transformers и torchvision).

### 2) Принцип работы модели и причины выбора

**Модель:** YOLO26n (nano, 2.41M параметров, 5.5 GFLOPs). Для сравнения взяты YOLO11n и YOLO26s.

Как работает детектор YOLO:
1. **One-stage детекция.** Сеть за **один проход** по кадру предсказывает рамки (bbox), классы и уверенность. Отсюда название: You Only Look Once. Two-stage детекторы (Faster R-CNN) сначала ищут регионы-кандидаты, потом классифицируют каждый. Так точнее, но медленнее.
2. **Backbone** (свёрточная сеть) извлекает признаки. **Neck** смешивает признаки разных масштабов: крупные объекты видны на «грубых» картах, мелкие на детальных. **Head** выдаёт предсказания.
3. **NMS (Non-Maximum Suppression).** Классические YOLO выдают много пересекающихся рамок на один объект, и NMS оставляет самую уверенную. Перекрытие меряется **IoU** (площадь пересечения / площадь объединения). YOLO26, по заявлению Ultralytics, обучена как end-to-end модель без NMS: одна рамка на объект получается сразу. Это упрощает и ускоряет постобработку, особенно на слабом железе.
4. **Порог уверенности `conf`:** рамки ниже порога отбрасываются.

**Трекинг (ByteTrack).** Детектор работает с каждым кадром независимо и «не знает», что человек на кадре 10 и на кадре 11 один и тот же. Трекер связывает детекции соседних кадров: предсказывает положение объекта (фильтр Калмана) и сопоставляет рамки по IoU. Особенность ByteTrack: он использует и низкоуверенные детекции, чтобы не терять объект при частичном перекрытии. Каждый трек получает ID, и так появляется возможность считать **уникальные** объекты.

**Видео = последовательность кадров:** OpenCV читает кадр → модель → рисуем рамки → пишем кадр в выходной файл.

**Обучение модели:** COCO, 80 классов, ~118k изображений.

**Причины выбора:**
- стандарт индустрии для детекции в реальном времени;
- nano-версия быстрая даже на CPU;
- YOLO26 это новейшая версия в установленной Ultralytics 8.4.163, а YOLO11n (из исходного плана) взята для сравнения поколений.

### 3) Структура данных

**Данные обучения:** MS COCO 2017, ~118k изображений с разметкой рамок для 80 классов (person, car, truck, bicycle, dog...).

**Видео для инференса:** `vtest.avi` из открытого набора тестовых данных OpenCV (`opencv/samples/data`). Уличная съёмка со статичной камеры: пешеходы, припаркованные машины.

| Параметр | Значение |
|---|---|
| Кадров | 795 |
| FPS | 10 |
| Длительность | ~80 с |
| Разрешение | 768×576 |

Разметки (ground truth) к видео нет, поэтому ML-качество оценивается отдельно на **coco8**. Это 4 валидационных изображения COCO с 17 размеченными объектами, демонстрационный набор Ultralytics.

**Формат инференса:** кадр BGR `H×W×3` (uint8) → N объектов, каждый это `(x1, y1, x2, y2)`, класс, уверенность, (ID трека).

### 4) Метрики качества

#### ML-метрики: coco8 (batch=1)

| Модель | Precision | Recall | mAP50 | **mAP50-95** |
|---|---|---|---|---|
| YOLO26n | 0.904 | 0.628 | 0.935 | **0.654** |
| YOLO11n | 0.574 | 0.850 | 0.814 | **0.608** |

- **mAP (mean Average Precision)** это главная метрика детекции. Для каждого класса строится кривая precision-recall при разных порогах уверенности, площадь под ней даёт AP, среднее по классам даёт mAP.
- **mAP50:** рамка засчитывается, если IoU с эталоном ≥ 0.5. **mAP50-95:** среднее по порогам IoU от 0.5 до 0.95. Эта метрика строже и требует точного положения рамки.
- P и R приведены для порога, где F1 максимален. YOLO26n «осторожнее»: высокая точность, ниже полнота. YOLO11n наоборот.
- **Важно:** coco8 содержит всего 17 объектов. Это демонстрация того, как считается метрика, а не оценка качества модели. Для честного сравнения нужна полная COCO val (5000 изображений). Опубликованные значения mAP на ней приведены в документации Ultralytics.

#### Метрики на видео (YOLO26n, conf=0.4, MPS, полный прогон с трекингом)

| Показатель | Значение |
|---|---|
| Детекций на кадр (в среднем) | 7.59 |
| Средняя уверенность | 0.735 |
| Детекции по классам (сумма по кадрам) | person 4478, truck 797, car 756, frisbee 2 |
| Уникальных объектов (по ID трека) | person 42, truck 2, car 1, frisbee 1 |

**Как читать:**
- **Детекции ≠ уникальные объекты.** Один человек, проходящий через кадр за 10 секунд, даёт ~100 детекций. Поэтому 4478 детекций людей превращаются всего в 42 трека.
- **42 трека это верхняя оценка числа людей.** При перекрытиях и выходе из кадра трекер может потерять человека и выдать ему новый ID (ID switch). Реальное число людей меньше.
- **car / truck:** в кадре стоят две припаркованные машины, одна из них белый фургон. Модель называет его то `car`, то `truck`, это пограничный класс COCO. Отсюда ~1550 детекций «машин» (примерно по одной на кадр на каждую) и смена класса у одного трека.
- **frisbee (2 детекции):** единичные ложные срабатывания, вероятно на светлых предметах на газоне.

#### Влияние порога уверенности (первые 300 кадров, YOLO26n, MPS)

| conf | Детекций на кадр | Средняя уверенность |
|---|---|---|
| 0.25 | 8.75 | 0.687 |
| 0.40 | 8.09 | 0.718 |
| 0.60 | 7.29 | 0.738 |

Порог это ручка **precision/recall**. Ниже порог означает больше найденных объектов, но и больше ложных срабатываний. Выше порог означает меньше ошибок, но часть людей (дальних, частично закрытых) теряется. Порог выбирается под задачу: для охраны важнее recall, для подсчёта статистики важнее precision.

#### Инфраструктурные метрики (первые 300 кадров, conf=0.4)

| Модель | Устройство | FPS (end-to-end) | Инференс, мс/кадр | Детекций на кадр |
|---|---|---|---|---|
| YOLO26n | **MPS** | **138.8** | 2.9 | 8.09 |
| YOLO26n | CPU | 46.0 | 20.3 | 8.09 |
| YOLO11n | MPS | 117.1 | 3.5 | 8.18 |
| YOLO26s | MPS | 69.9 | 3.8 | 8.45 |

- Все конфигурации работают **многократно быстрее реального времени**: видео идёт с 10 FPS, а даже CPU обрабатывает 46 FPS. Полный прогон с трекингом и записью видео дал 93.5 FPS.
- MPS быстрее CPU в ~3 раза по FPS end-to-end и в ~7 раз по чистому инференсу. Детекции на MPS и CPU совпадают (8.09 на кадр).
- YOLO26n быстрее YOLO11n. Отсутствие NMS упрощает постобработку.
- YOLO26s (small, крупнее) находит больше объектов и увереннее (0.788 против 0.718), но вдвое медленнее.
- **Замечание про замер на MPS:** GPU выполняет операции асинхронно, поэтому `infer_ms` на MPS занижен: часть времени «перетекает» в постобработку. Надёжная метрика на MPS это FPS end-to-end.

#### Продуктовые метрики (для внедрения)

- точность подсчёта посетителей относительно ручного подсчёта;
- доля ложных тревог в смену;
- задержка от события до алерта.

### 5) Особенности реализации, эффективность и ограничения

**Реализация:**
- Покадровая обработка через OpenCV (`VideoCapture` → модель → `r.plot()` → `VideoWriter`) вместо встроенного `save=True`, чтобы видеть и контролировать каждый шаг и собирать свою статистику.
- Режим трекинга: `model.track(frame, persist=True, tracker="bytetrack.yaml")`. `persist=True` сохраняет состояние трекера между кадрами.
- Прогревочный кадр перед замером.

**Найденные проблемы и решения** (материал для отчёта об особенностях реализации):
1. **«Прилипание» трекера к модели.** `model.track(persist=True)` регистрирует колбэки трекера на объекте модели. Если потом этот же объект использовать для `predict`, результаты тоже проходят через трекер, и сравнение порогов даёт нелогичные цифры (при conf=0.25 детекций было меньше, чем при 0.4). **Решение:** отдельный экземпляр модели на каждый прогон.
2. **Батчевый инференс на MPS даёт неверные результаты.** Валидация на MPS с batch > 1 дала mAP50-95 0.107 вместо 0.654, причём и для YOLO26n, и для YOLO11n. С `batch=1` результаты на MPS и CPU совпадают до третьего знака. Видео обрабатывается покадрово (batch = 1), поэтому результаты по видео корректны. Валидация запускается с `batch=1`. Вероятно, это ошибка в связке PyTorch MPS и Ultralytics. Вывод: **результаты на GPU нужно сверять с CPU** хотя бы на небольшой выборке.

**Ограничения:**
1. **Мелкие и далёкие объекты** nano-модель теряет, особенно при высоком `conf`.
2. **Пограничные классы** (фургон: car или truck) нестабильны от кадра к кадру.
3. **ID switches** при перекрытиях людей завышают число уникальных объектов.
4. **Нет разметки** для своего видео, поэтому mAP на реальной задаче не измерен.

**Возможные улучшения (без обучения):**
- сглаживание класса по треку (голосование большинством по кадрам), чтобы фургон был одним классом;
- модель крупнее (`s`/`m`) при запасе по FPS: в нашем случае запас огромный (70 FPS против 10 FPS видео);
- BoT-SORT с re-identification для уменьшения ID switches;
- обработка каждого N-го кадра для слабого железа;
- экспорт в CoreML для максимальной скорости на Apple Silicon.

## 5. Локальная LLM: чат-ассистент (Ollama)

Скрипт: `task1-ml-models/llm_local.py`
Запуск: `uv run python task1-ml-models/llm_local.py` (нужен запущенный `ollama serve` и модели `qwen3:8b`, `gemma4:e4b`)
Полные ответы моделей: `task1-ml-models/results/llm_local.jsonl`

### Постановка задачи (ТЗ)

Локальный чат-ассистент без интернета и сторонних API: данные не уходят с машины.

- **Вход:** список сообщений чата `[{"role": "user", "content": prompt}]`.
- **Выход:** текст ответа и телеметрия: `ttft_s`, `tok_per_s`, `eval_tokens`, `load_ms`.
- **Сценарий использования:** ассистент разработчика, которому нельзя отправлять код и логи во внешние API.
- **Требования:** модель помещается в 24 ГБ unified memory, TTFT ≤ 500 мс на прогретой модели, генерация ≥ 20 токенов/с.

### 1) Преимущества выбранного инструмента (Ollama)

- **Одна команда до работающей LLM:** `ollama pull` скачивает квантизованные веса, `ollama serve` поднимает HTTP-сервер на `localhost:11434`.
- **Ускорение на Apple Silicon:** движок llama.cpp (Metal, формат GGUF) и движок MLX. `ollama ps` показывает `100% GPU`.
- **Телеметрия в ответе:** последний чанк стрима содержит `load_duration`, `prompt_eval_count`, `eval_count`, `eval_duration` в наносекундах. Скорость считается без внешних профилировщиков.
- **Работа офлайн.** На машине задан системный прокси, поэтому клиент создаётся с `trust_env=False`: запросы к `localhost` не идут через прокси.

### 2) Принцип работы модели и причины выбора

Сравниваются две модели разных семейств и движков:

| Модель | Семейство | Движок / формат | Память (`ollama ps`) |
|---|---|---|---|
| `qwen3:8b` | Qwen3, Alibaba | llama.cpp / GGUF Q4_K_M | ~5.2 ГБ при `num_ctx=8192` |
| `gemma4:e4b` | Gemma 4, Google | MLX / NVFP4 | 9.5 ГБ при `num_ctx=4096` |

Как работает:
1. **Decoder-only трансформер.** Модель предсказывает следующий токен по всем предыдущим и повторяет шаг (авторегрессия). Чат это текст с разметкой ролей (chat template), который модель продолжает. При `temperature=0` выбирается самый вероятный токен.
2. **Prefill и decode.**
   - Prefill: весь промпт обрабатывается за один параллельный проход. Эта фаза определяет **TTFT** (time to first token).
   - Decode: токены генерируются по одному. На каждый токен нужно прочитать все веса из памяти, поэтому скорость **tokens/s** ограничена пропускной способностью памяти.
3. **KV-cache.** Ключи и значения attention для уже обработанных токенов хранятся в памяти. Новый токен не пересчитывает весь контекст. Цена: память растёт линейно с длиной контекста.
4. **Квантизация.** 8B параметров в fp16 занимают ~16 ГБ. 4-битные веса (Q4_K_M, NVFP4) занимают ~5 ГБ и читаются из памяти в ~3–4 раза быстрее. Потеря качества небольшая.
5. **Режим рассуждения отключён (`think=False`).** Обе модели умеют сначала писать скрытое рассуждение. Для честного замера TTFT и скорости режим выключен.

**Причины выбора:**
- `qwen3:8b` это модель из плана: open-weights, хорошо знает русский, 8B помещается в 24 ГБ с запасом.
- `gemma4:e4b` это модель другого семейства и другого движка (MLX). Сравнение показывает разницу движков GGUF и MLX на одном железе.

### 3) Структура данных

- **Данные обучения:** веб-корпуса из триллионов токенов (тексты, код, математика), затем instruction tuning и выравнивание по предпочтениям. Модели мы не обучали.
- **Данные проверки:** 9 промптов разных типов: фактология, арифметика, код, перевод, суммаризация, логическая задача, вопрос по ML на русском, провокация на галлюцинацию (несуществующий роман), поиск уязвимости в коде.
- **Формат инференса:** список сообщений → chat template → поток чанков → `{"text", "ttft_s", "tok_per_s", "eval_tokens", "load_ms"}`.
- **Параметры:** `temperature=0`, `num_predict=256` (лимит длины ответа), `think=False`.

### 4) Метрики качества

#### Инфраструктурные метрики (Apple M5, 24 ГБ)

| Модель | Холодная загрузка | TTFT (среднее, диапазон) | Decode (среднее, диапазон) |
|---|---|---|---|
| `qwen3:8b` | 2.0 с | 200 мс (189–224) | 22.2 tok/s (21.2–23.3) |
| `gemma4:e4b` | 5.3 с | 184 мс (125–289) | **83.6 tok/s** (57.2–136.9) |

- TTFT прогретых моделей ~200 мс. Требование ≤ 500 мс выполнено для обеих.
- `gemma4:e4b` на MLX генерирует в **3.8 раза быстрее** `qwen3:8b` на GGUF, хотя занимает больше памяти.
- Холодная загрузка (первый запрос) в 10–30 раз дольше обычного TTFT. Её не смешиваем с латентностью запроса.

#### Качество на 9 промптах

Оценка вручную по полным ответам: `PASS` верно; `PARTIAL` суть верна, есть неточность или ответ обрезан; `FAIL` ошибка или галлюцинация.

| Категория | `qwen3:8b` | `gemma4:e4b` |
|---|---|---|
| factology: столица Австралии и год | `PARTIAL`: Канберра, но 1901 (год Федерации; Канберру выбрали в 1908) | `PASS`: Канберра, 1908 |
| arithmetic: `47 * 83 + 129` | `PARTIAL`: шаги верны (3901), ответ 4030 обрезан лимитом 256 токенов | `PASS`: 4030 |
| code: `is_prime` за `O(sqrt(n))` | `PASS` | `PASS`: с оптимизацией шага `6k +/- 1` |
| translation: фраза про квантизацию | `PARTIAL`: autoregressive переведено как «автосегментной» | `PARTIAL`: перевод верный, но дала 3 варианта вместо одного |
| summarization: ≤ 20 слов | `PASS`: 13 слов | `PASS`: 16 слов |
| logic: 3 лампочки и выключатели | `PASS`: решение через нагрев лампы | `FAIL`: включила 2 выключателя, решение противоречиво |
| russian_ml: prefill и decode | `PARTIAL`: prefill описан размыто | `PASS` |
| hallucination_guard: несуществующий роман Достоевского | `FAIL`: выдумала сюжет и «настоящее название» | `PASS`: ответила, что такого романа нет |
| code_security: SQL в f-строке | `PASS`: SQL-инъекция и параметризованный запрос | `PARTIAL`: верное объяснение, исправленная строка обрезана лимитом |
| **Итого** | **4 PASS / 4 PARTIAL / 1 FAIL** | **6 PASS / 2 PARTIAL / 1 FAIL** |

#### Продуктовые метрики (для внедрения)

- доля ответов, принятых пользователем без правок;
- доля галлюцинаций на вопросах о фактах;
- время ответа целиком при типичной длине ответа (например, 300 токенов: ~14 с у `qwen3:8b`, ~4 с у `gemma4:e4b`).

### 5) Особенности реализации, эффективность и ограничения

**Реализация:**
- Стрим `CLIENT.chat(..., stream=True, think=False)`. TTFT замеряется на клиенте до первого непустого чанка, tokens/s считается по серверным счётчикам `eval_count / eval_duration`. Так сеть не влияет на оценку скорости GPU.
- Первый запрос каждой модели («прогрев») из замеров исключён, он показывает время холодной загрузки.
- Модели иногда вставляют эмодзи в ответ. Скрипт удаляет их перед записью в `results/llm_local.jsonl`.

**Ограничения:**
1. **Галлюцинации без контекста.** `qwen3:8b` уверенно пересказала несуществующий роман. Без внешних фактов (RAG, инструменты) ответам LLM доверять нельзя. Для фактических вопросов ответ нужно опирать на найденные источники и проверять отдельно.
2. **`think=False` ускоряет, но вредит логике.** `gemma4:e4b` без рассуждения ошиблась в задаче про лампочки.
3. **Лимит `num_predict=256` обрезает подробные ответы.** Модели многословны: 5 ответов из 18 упёрлись в лимит. Лимит надо поднимать или просить короткий ответ явно.
4. **Ручная оценка на 9 промптах.** Это качественная проверка, а не статистика. Для выводов о качестве нужны стандартные бенчмарки (MMLU, HumanEval) или LLM-as-a-judge на большой выборке.
5. **Память.** KV-cache растёт с `num_ctx`: при 32K токенов контекста модель занимает на несколько ГБ больше. Две модели одновременно в 24 ГБ требуют аккуратного выбора `num_ctx`.

## Выводы

1. **Готовые модели закрывают типовые задачи без обучения.** На всех пяти задачах требования ТЗ по качеству и скорости выполнены на ноутбуке, без GPU-кластера и облачных API.
2. **GPU Apple Silicon (MPS) даёт выигрыш от 2.4x (DistilBERT) до ~11x (ResNet-50).** Свёрточные сети параллелятся лучше всего. Для маленьких моделей и коротких входов выигрыш меньше: накладные расходы на передачу данных сравнимы с вычислением.
3. **Честная проверка важнее красивой цифры.** Тональность проверяли на IMDB, а не на SST-2, на котором модель обучалась. WER считали с одинаковой нормализацией. На видео отделили детекции от уникальных объектов через трекинг. mAP на coco8 подан как демонстрация метрики, а не как оценка модели.
4. **Размер модели это компромисс качество/скорость.** whisper-small точнее tiny почти вдвое по WER. YOLO26s увереннее YOLO26n, но вдвое медленнее. `gemma4:e4b` на MLX в 3.8 раза быстрее `qwen3:8b`.
5. **LLM без внешних фактов галлюцинирует.** `qwen3:8b` пересказала несуществующий роман. Без опоры на источники (RAG, инструменты) и проверки ответов LLM нельзя использовать для фактических вопросов.
6. **Для обёртки в API лучше всего подходит модель тональности:** лёгкая, быстрая, без состояния, вход и выход легко сериализуются в JSON.
